Kode berjalan dari atas ke bawah — sampai tidak lagi. Begitu ada satu baris yang harus menunggu sesuatu yang lambat, seperti respons jaringan atau timer, JavaScript punya dua pilihan: membekukan semuanya sampai selesai, atau tetap jalan dan menangani hasilnya belakangan. Pilihan itulah yang jadi perbedaan utama antara kode synchronous dan asynchronous.

## Kode Synchronous

Kode synchronous berjalan satu baris pada satu waktu, berurutan, dan setiap baris harus selesai dulu sebelum baris berikutnya dimulai. Tidak ada hal lain yang terjadi selama operasi synchronous sedang berjalan.

```js
console.log('Start');

function heavyLoop() {
  let total = 0;
  for (let i = 0; i < 1e9; i++) total += i;
  return total;
}

console.log(heavyLoop()); // seluruh aplikasi menunggu di sini
console.log('End');
```

Loop itu bisa memakan waktu cukup terasa untuk selesai, dan selama itu tidak ada hal lain yang berjalan. Tidak ada click handler, tidak ada re-render, tidak ada apa pun. Di tab browser, itu artinya halaman jadi beku. Inilah yang dimaksud "blocking": operasi tersebut menguasai main thread sampai selesai, dan semua yang lain harus antre di belakangnya.

## Kode Asynchronous

Kode asynchronous membiarkan operasi yang lambat berjalan di latar belakang (di luar main thread, lewat API milik browser atau Node) sehingga sisa program tetap jalan alih-alih menunggu.

```js
console.log('Start');

fetch('/api/data')
  .then((res) => res.json())
  .then((data) => console.log(data));

console.log('End');
```

Di sini, `'End'` tercetak lebih dulu sebelum data hasil fetch, padahal `fetch()` ditulis lebih awal dalam file. Request-nya dimulai, JavaScript langsung lanjut, dan callback `.then()` baru berjalan setelah responsnya benar-benar datang, kapan pun itu.

Kamu akan terus menemui operasi asynchronous dalam kode sungguhan, hampir selalu karena ada sesuatu di luar programmu yang harus terjadi lebih dulu:

- **Network request**: `fetch()`, panggilan API, memuat script dari CDN
- **Timer**: `setTimeout()`, `setInterval()`
- **File dan disk I/O**: membaca file di Node, menulis ke IndexedDB di browser
- **Input pengguna**: menunggu klik, ketikan, atau submit form
- **Query database**: apa pun yang harus round-trip ke server database

Tidak satu pun dari ini selesai secara instan, dan tidak satu pun waktunya bisa dikontrol langsung oleh JavaScript. Itulah sebabnya semuanya diserahkan, bukan dijalankan langsung di tempat.

## Tiga Cara Menulis Kode Asynchronous

JavaScript sudah melewati tiga generasi sintaks async, dan kamu masih akan menemui ketiganya di kode sungguhan.

### Callback

Mengoper sebuah fungsi untuk dijalankan setelah operasi selesai:

```js
fs.readFile('data.txt', (err, data) => {
  if (err) throw err;
  console.log(data);
});
```

Sederhana untuk satu langkah async, tapi menyulitkan begitu kamu butuh beberapa langkah berurutan. Callback bersarang di dalam callback lain adalah asal-usul istilah "callback hell".

### Promise

Objek yang merepresentasikan nilai yang belum siap, dirangkai dengan `.then()`:

```js
readFilePromise('data.txt')
  .then((data) => console.log(data))
  .catch((err) => console.error(err));
```

Rangkaian ini meratakan masalah nesting dan memberimu satu `.catch()` untuk error, bukan mengecek `err` di setiap langkah.

### Async/await

Syntax sugar di atas promise yang membuat kode async terbaca seperti kode synchronous:

```js
async function loadData() {
  try {
    const data = await readFilePromise('data.txt');
    console.log(data);
  } catch (err) {
    console.error(err);
  }
}
```

Perilakunya sama dengan versi promise, tapi terbaca dari atas ke bawah seperti contoh synchronous di awal artikel ini. Itulah daya tariknya.

## Perbedaan Utama

Berdampingan, trade-off-nya bisa diringkas jadi satu pertanyaan: apakah operasi ini bergantung pada sesuatu di luar kodemu sendiri untuk selesai lebih dulu?

| | Synchronous | Asynchronous |
| --- | --- | --- |
| Eksekusi | Satu baris pada satu waktu, berurutan | Pekerjaan lambat berjalan di latar belakang |
| Main thread | Terblokir sampai operasi selesai | Tetap bebas selama menunggu |
| Urutan hasil | Sesuai urutan di kode | Bergantung kapan tiap operasi selesai |
| Ditulis dengan | Pemanggilan fungsi biasa | Callback, promise, `async`/`await` |
| Cocok untuk | Pekerjaan cepat, murni CPU | Network request, timer, file/disk I/O |

## Kenapa Ini Penting

Jadi kenapa tidak menulis semuanya secara asynchronous saja? Karena kode async lebih sulit dipahami: hasil bisa datang dengan urutan berbeda dari yang kamu tulis, dan setiap `await` adalah titik di mana sisa fungsi harus menunggu giliran di belakang apa pun yang sedang berjalan. Kode synchronous lebih sederhana justru karena hal itu tidak mungkin terjadi: satu hal terjadi, lalu yang berikutnya, selalu sesuai urutan di halaman. Trade-off-nya, satu panggilan synchronous yang lambat membekukan semua yang ada di belakangnya, termasuk UI, sementara kode asynchronous menjaga aplikasi tetap responsif dengan tambahan kompleksitas itu sebagai harganya.

[Debouncing](/writing/id/debouncing) pada input pencarian adalah contoh bagus dari trade-off ini di dunia nyata: pemanggilan `fetch()` di dalamnya bersifat asynchronous justru supaya ketikan tidak membeku selama request berlangsung. Kalau kamu ingin mekanisme yang lebih dalam (bagaimana JavaScript sebenarnya memutuskan kapan sebuah callback yang tertunda boleh berjalan), itulah yang dibahas di [event loop](/writing/id/event-loop), satu lapis di bawah pembagian sync/async yang dijelaskan di sini.
