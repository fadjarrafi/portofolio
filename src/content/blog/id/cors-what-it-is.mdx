Kalau kamu pernah membangun aplikasi web, kemungkinan besar pernah bertemu error ini. Buat aku pun ini sempat jadi mimpi buruk waktu pertama kali kena, saat lagi belajar bikin API untuk sebuah blog. Untuk paham kenapa error ini muncul, kita perlu tahu apa itu CORS dan bagaimana cara kerjanya.

## Same-origin policy

Secara default, browser hanya mengizinkan sebuah halaman meminta sumber daya dari origin-nya sendiri — domain, protokol, dan port yang sama. Inilah same-origin policy (SOP), yang membatasi bagaimana skrip dari satu origin bisa menjangkau sumber daya di origin lain.

Misalnya kamu punya aplikasi web di `https://www.domain-a.com` yang butuh data dari API di `https://api.domain-b.com`. Karena origin-nya berbeda, ini disebut cross-origin request — dan secara default SOP memblokirnya.

<div className="flex justify-center">
  <img src="/static/cors/cross-origin-request.png" alt="Cross-origin request diblokir oleh same-origin policy" width="700" />
</div>

Lalu bagaimana kalau aplikasi kita memang perlu berkomunikasi dengan origin lain? Di sinilah CORS berperan.

## Apa itu CORS

Cross-origin resource sharing adalah cara sebuah server memberi tahu browser origin mana saja yang boleh mengakses sumber dayanya. Mekanismenya lewat header HTTP yang ditambahkan ke respons — browser membaca header itu lalu memutuskan apakah datanya boleh diberikan ke skrip kita.

Ada beberapa [header CORS](https://fetch.spec.whatwg.org/#http-cors-protocol), tetapi yang utama adalah:

- `Access-Control-Allow-Origin`
- `Access-Control-Allow-Methods`
- `Access-Control-Allow-Headers`

Untuk request sederhana seperti `GET`, `POST`, atau `HEAD`, browser langsung mengirimnya ke server sambil menyertakan header `Origin` yang menandakan asal request.

<div className="flex justify-center">
  <img src="/static/cors/cors-request.png" alt="Request dan respons CORS bertukar header Origin dan Access-Control-Allow-Origin" width="700" />
</div>

#### Request dari browser:

```
GET /data HTTP/1.1
Host: api.domain-b.com
Origin: https://www.domain-a.com
```

#### Respons dari server:

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://www.domain-a.com
Content-Type: application/json

{ "message": "Hello from domain-b!" }
```

Kalau respons mengembalikan `Access-Control-Allow-Origin` yang cocok dengan origin kita, browser meneruskan datanya. Kalau tidak, browser memblokirnya — itulah error di awal tulisan ini.

Request yang bisa mengubah data — `DELETE`, `PUT`, `PATCH`, atau request dengan header kustom — diperlakukan lebih hati-hati. Sebelum mengirim request aslinya, browser melakukan **preflight**: sebuah request `OPTIONS` untuk menanyakan ke server apakah request aslinya diizinkan.

#### Request preflight `OPTIONS` dari browser:

```
OPTIONS /data HTTP/1.1
Host: api.domain-b.com
Origin: https://www.domain-a.com
Access-Control-Request-Method: DELETE
Access-Control-Request-Headers: Content-Type
```

#### Respons preflight `OPTIONS` dari server:

```
HTTP/1.1 204 No Content
Access-Control-Allow-Origin: https://www.domain-a.com
Access-Control-Allow-Methods: GET, POST, DELETE, OPTIONS
Access-Control-Allow-Headers: Content-Type
```

Setelah preflight lolos, browser mengirim request aslinya dan menerima responsnya.

#### Request `DELETE` dari browser:

```
DELETE /data/123 HTTP/1.1
Host: api.domain-b.com
Origin: https://www.domain-a.com
Content-Type: application/json
```

#### Respons dari server:

```
HTTP/1.1 200 OK
Access-Control-Allow-Origin: https://www.domain-a.com
Content-Type: application/json

{ "message": "Resource deleted successfully!" }
```

## Kenapa CORS penting

CORS membuat server yang menentukan siapa saja yang boleh membaca sumber dayanya. Tanpa itu, situs mana pun bisa diam-diam mengirim request ke domain lain atas nama pengguna — dasar dari serangan seperti [cross-site request forgery (CSRF)](https://owasp.org/www-community/attacks/csrf). Dengan CORS, aplikasi tetap bisa berbagi data lintas origin, tapi hanya kalau server secara eksplisit mengizinkannya.
